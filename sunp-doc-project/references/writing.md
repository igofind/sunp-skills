# 阶段二：写作

产出的是**参考手册（reference）**：供人工作时按主题查阅，注重信息完整与可定位。每篇按 `templates.md` 的骨架组织；不需要的小节删掉，不留空标题。用简体中文和中文语法，符合中文阅读习惯；类名、方法名、配置项、路径、命令保留原文。

## 内容规则

- 一篇一主题：每篇包含该主题完整的结论、数据与源码位置，读者只读本篇就能查到本主题的信息；跨文档链接只做导航，不用「详见 XX」替代本篇该写的内容。
- 定位写法：用目录树、Controller 名、类名、方法名、表名、配置键、URL 等名称级线索，读者可据此在代码里检索到位置，不要求逐条给行号；证据能回到源码即可，行号不可靠就不写。
- 区分事实与判断：代码可见的事实直接写；由证据推导的判断标注「待确认」；不凭类名、配置名或注释断言功能已上线。
- 不复制大段源码；正文只留结论与定位线索。

## 排版纪律

这部分决定文档读起来是否费劲。信息形态决定承载方式，不为整齐强行表格化。

| 信息形态 | 承载方式 | 反例 |
|---|---|---|
| 二维数据：字段、模块、枚举、配置、统计 | 短表格，一列一个短值 | 一列里塞整段长路径或长说明 |
| 目录树、配置、命令、SQL、状态流转、代码片段 | 代码块 | 把长路径拆散写进表格单元格 |
| 架构、分层、请求链、ER、数据流 | mermaid 图 | 用大段文字描述层级关系 |
| 一维清单：接口、参数、步骤、注意事项、功能点 | 列表 | 把一维清单拉成多列表格 |

- 表格只放二维数据：行是同类条目，列是固定属性；单列信息改列表，长单元格拆成列表或代码块。
- 表格前后各留一句说明：前面说清这张表是什么，后面点出需要注意的结论，不让读者面对一张没有引导的表。
- 图前后各留一句说明：前面用「图 N：……」给出编号与标题，说明图表达什么；后面点出图中需要注意的结论。
- 图的编号按篇内出现顺序从 1 递增；数据库设计等以编号命名的章节，图号沿用章节编号（如图 [N+2]）。
- 长路径只出现在代码块或行内 code 里；单元格内最多一个行内 code 符号。

## 表达规则

以下规则让句子更易读、易懂，适用于全部文档。规则出处见本 skill 的参考资料台账。

**人称与视角**

- 描述事实时以项目、模块、服务、接口为主语，用第三人称或无主语句，不用「你」。
- 只在需要读者执行动作时用祈使句，不必刻意加「你」。
- 不用「我们」；「用户」只指软件的使用者，不指文档读者。
- 全文主语视角保持一致，开头写明预期读者是谁。

**语态与句式**

- 用主动语态，让做动作的人或模块作主语；少用「被」字句，只有强调对象或执行者无关时才用被动。
- 先说条件、场景或目标，再说动作，让读者能跳过与自己无关的部分。例如「要构建项目，先安装依赖」，不写「先安装依赖，如果你要构建项目」。
- 描述一般行为用习惯性陈述，不写「将会」等将来时推测。

**简洁与标题**

- 先给结论和下一步，再补依据；关键词前置，便于扫读；删掉铺垫、套话、重复和与当前主题无关的内容。
- 列表项以关键词或动词开头，避免「你可以」、「有……」等弱写法。
- 标题写清本节讲什么或得出什么结论，同级句式一致；标题末尾不加句号或冒号。

## 自检与修正

逐项检查，任一项不合格就按问题当场修改，修改后重新从头检查，直到全部合格再交付：

**内容**
- [ ] 主题完整：本篇含该主题完整信息，读者不必读其他文档就能查到；跨文档链接只做导航，不用「详见 XX」替代本篇内容
- [ ] 定位线索：关键信息给出目录树、Controller 名、类名、表名或 URL，读者可据此检索到源码
- [ ] 没有臆造：事实与判断分开，无证据处标「待确认」，不把静态证据写成线上事实
- [ ] 关系呈现：本篇内的关系与数据流用图或表格讲清，不用大段文字堆砌，关键关系未省略

**排版**
- [ ] 承载得当：二维数据用短表格，目录/配置/命令/SQL/代码用代码块，架构/关系/流程用图，一维清单用列表
- [ ] 表格简短：单元格一行可读，无长路径或长段落塞进单元格，单列信息已改列表
- [ ] 表格有引导：每张表前有说明、后有结论点出
- [ ] 结构一致：同类型文档沿用同一骨架，术语全篇一致

**表达**
- [ ] 表达易读：主动语态、条件前置、主语视角一致，无英文直译腔与弱写法
- [ ] 标题清晰：写清本节内容或结论，同级句式一致，末尾无标点
