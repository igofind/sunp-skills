# 语言无关通用规则

按下列维度审查，语言特有规则见各语言文件。

## 审查原则

- 风格以规范为准；规范未作规定时以项目现有风格为准；两者皆无时保持局部一致
- 技术事实与数据优先于个人偏好；偏好性意见标为 Nit，不作为「必须改」
- 只报当前代码确实存在的问题，不为凑数制造问题
- 结论能回到具体代码位置，不凭类名或注释推断

## 格式与排版

- 缩进、行宽、换行、空白、括号、分号、逗号符合该语言规范
- 文件结构清晰，声明与导入顺序符合约定
- 字符编码统一

## 命名

- 名称完整表达对象的用途与语义，不长到难以阅读
- 大小写与构词符合该语言规范
- 同类实体命名方式一致；不使用含义不明或易误解的名称

## 注释与文档

- 注释解释「为什么」，不复述代码「做什么」；代码本身能说清的不写注释
- 注释与实现保持同步；过时注释标为待确认
- 公开接口、模块、类、函数按该语言规范提供文档说明
- 不主动为既有代码补注释，除非本次修改使其失准

## 结构与复杂度

- 函数与类职责单一，长度与嵌套在可读范围内
- 命名、控制流、错误处理直白，不引入超出当前需求的通用性
- 不保留未使用的变量、字段、参数、导入与注释掉的代码

## 一致性

- 同类实体在命名、结构、错误处理方式上保持一致
- 与项目现有风格冲突时，指出冲突并说明依据，不假设项目一定正确

## 修改建议写法

- 针对代码，不针对作者
- 说明依据与理由，让被审查者理解改动的价值
- 区分「指出问题」与「给出方案」：问题明确时给方向，方案有多种时说明取舍
- 按必须改、建议改、Nit 分级，避免把偏好当硬性要求
