# Java 审查规则

审查依据分两层：先按 Google Java Style Guide 检查格式、命名、编程实践与 Javadoc；再按项目自定义要求检查结构、复杂度与注释。两层冲突时，项目自定义要求优先。

## 格式与源文件结构

- UTF-8 编码；文件名与公开类名一致
- 包声明在导入之前；导入不用通配符，静态导入单独成组
- 缩进为 4 个空格，列宽上限 120，一行不超过一条语句
- 大括号与换行、空白、括号分组符合规范；续行缩进统一

## 命名

- 包名全小写；类名 UpperCamelCase；方法名、参数名、局部变量 lowerCamelCase
- 常量 UPPER_SNAKE_CASE；类型变量用单个大写字母或 UpperCamelCase
- 名称完整达意，不用缩写堆砌；同类实体命名方式一致

## 编程实践

- 覆写方法带 `@Override`
- 捕获的异常不被忽略，说明处理或向上抛出
- 静态成员通过类名访问
- 不使用 finalize

## 项目自定义要求

以下要求源自项目全局约定，按结构、命名、注释、复杂度与防御四个维度归纳。可判定标准用于统一尺度，避免凭感觉判断。

### 结构

- 最小充分：每个新增结构（变量、字段、常量、方法、参数、分支、枚举值、抽象层、配置项）都由当前需求直接支撑；无证据支撑的判为过度设计
- 复用优先：涉及工具类时先查项目已封装的工具模块与已引入的第三方库，有匹配实现就复用，不另造
- 无冗余：未使用的变量、字段、参数、导入与注释掉的代码一律移除
- 不预留：不为尚未提出或确认的需求预留参数、分支、抽象与配置

### 命名与实现组织

- 清晰优先：命名直白，优先用卫语句和提前返回简化控制流，避免层层嵌套与技巧化写法
- 范式匹配：以函数和流程组织；项目既有代码采用面向对象范式时以项目约定为准，不强行引入类、继承与多态

### 注释

- 语义优先：注释写语义，不复述代码；新增的类型别名、常量、函数或方法（含嵌套具名函数；内联回调与 import 不算）各写 1-2 句，分别说明其表示什么、是什么、做什么
- 形式沿用：注释形式沿用项目约定，改实现时同步更新注释
- 既有克制：不主动为既有代码补注释；仅当本次修改使既有注释失准时指出

### 复杂度与防御

- 调用可达：方法须有实际调用点
- 参数必要：参数须在调用点存在两种以上不同实参；无两种不同取值即判为冗余参数
- 分支可达：分支须有当前可达场景
- 抽象有据：抽象须有两处以上实现或调用
- 配置有用：配置项须至少有一个非默认取值被实际使用
- 防御具体：异常处理与防御校验须能指明具体且可复现的失败来源，泛化捕获不保留

## Javadoc

- 格式符合规范，摘要片段完整
- 公开类、公开方法与字段按要求提供 Javadoc，说明用途、用法与行为
