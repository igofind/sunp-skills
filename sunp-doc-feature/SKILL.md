# 指定功能现状文档

## 用途与边界

针对一个指定功能，产出**代码的结构化镜像**：功能拆成 section，section 标注代码位置和实现细节清单，让人和 AI 都能顺着文档找到代码、不丢细节。

与项目全景文档不同，本 skill 聚焦单个功能的内部结构、业务规则和边界条件，产出可反向翻译回代码的中间表示。文档表达按结论先行、术语准确、结构清晰、篇幅适中的要求执行。

## 核心概念：文档是代码的镜像

文档与代码是同一棵树的两种表示：代码给编译器执行，文档给人和 AI 理解，带组织、说明和关系。两者可双向翻译：

- 反向翻译：代码 → 文档（梳理功能现状、代码审查）
- 正向翻译：需求 → 文档 → 代码（新功能开发）

翻译是本 skill 的核心操作。不跳过文档直接写代码，先生成或理解文档，再从文档翻译为代码。

## 文档结构

```
docs/
├── project-manifest.yml          # 项目级清单（仅跨功能依赖时创建）
├── <feature>/                    # 功能目录
│   ├── manifest.yml              # 功能级清单
│   ├── 1-xxx.md                  # section 内容
│   └── 2-xxx.md
└── shared/                       # 跨功能共享 section
    └── name-to-code-conversion.md
```

manifest 存元数据（sections 树、code_ref、关系与状态），`.md` 存 section 内容（含实现细节清单）。只写当前任务涉及的 section，不创建空占位文件。字段与格式见 [`references/format.md`](references/format.md)，完整示例见 [`examples/`](examples/)。

## 工作流一：代码 → 文档（梳理功能现状）

触发：已有代码，要梳理某功能的现状。

1. **定位入口**：找到该功能的入口类 / 方法，确定分析范围（哪些文件、哪些包）。
2. **功能拆解**：按业务流程拆成独立功能节点，每个节点一句话说明「它做了什么」，生成功能目录与 `manifest.yml` 的顶层 sections。
3. **逐功能反向翻译**：代码类 → 类级 section（`code_ref` 为文件路径）；代码方法 → 方法级 section（`code_ref` 为 `{ file, method }`）；分支与校验 → 实现细节清单；边界条件 → 已知边界条件；调用关系 → `depends_on` / `references`。只提取「AI 不知道就会出错」的细节。
4. **跨功能关系**：被多个功能共享的逻辑提取到 `shared/`；功能间依赖标注在 manifest。
5. **概览与自检**：在 manifest 中汇总各功能状态，按下方校验清单逐项检查。

### 细节提取维度

对每个代码方法逐维度检查是否有需提取的细节，每个维度都明确回答「有」或「没有」，不适用也要标注，不能跳过：

| 维度 | 要提取的细节 |
|---|---|
| 数据转换 | 名称→编码、格式转换、类型转换 |
| 校验规则 | 必填、格式、范围、唯一性校验 |
| 校验失败处理 | 中断还是继续、错误信息、错误数据收集 |
| 文件 / 输出 | 生成文件的格式、命名、内容结构、保留策略 |
| 状态流转 | 状态枚举、转换条件、非法转换处理 |
| 外部交互 | 接口调用、消息发送、缓存操作 |
| 边界条件 | 空值、并发、超时、部分失败 |

### 反向翻译校验

- [ ] 每个代码类都有对应 section（`code_ref` 指向类文件）
- [ ] 每个代码方法都有对应 section（`code_ref` 指向方法）
- [ ] 每个方法级 section 都有实现细节清单
- [ ] 清单每条具体、可验证，不是笼统描述
- [ ] 已知边界条件已列出
- [ ] 调用关系已标注为 `depends_on` / `references`
- [ ] 共享逻辑已提取到 `shared/` 并标注 `references`

## 工作流二：需求 → 文档

触发：有新需求，没有已有代码作为主要参照。

1. **需求理解**：读需求材料，理解业务目标与约束；不确定的地方确认后再写。
2. **功能拆解**：按功能模块拆分，创建功能目录与顶层 sections。
3. **逐功能正向翻译**：业务规则 → section + 实现细节清单；校验条件与异常场景 → 已知边界条件。粒度到「AI 不知道就会出错」的层级。
4. **方案设计（可选）**：涉及架构决策时，给 2-3 个方案、说明取舍、给出推荐，生成 `design` 类型 section。
5. **任务拆分**：拆成可执行任务，每个任务设置 `depends_on` 与清单，生成 `task` 类型 section。
6. **关系标注**：更新 manifest 中的 `depends_on` / `references`。

校验：每个需求模块都有 section；每个 task 都有实现细节清单；清单条目具体可验证；边界条件已列出；`depends_on` 正确反映执行顺序；对照原始需求逐条确认无遗漏。

## 工作流三：文档 → 代码

触发：已有结构化文档，要翻译成代码。

1. **全局理解**：读 `manifest.yml` 理解整体结构与依赖图。
2. **确定范围**：找到 `status: pending` 的 section，按 `depends_on` 拓扑排序确定翻译顺序。
3. **前置检查**：所有 `depends_on` 与 `references` 的 section 必须为 `done`，否则保持 `pending` 不进入翻译。
4. **逐 section 翻译**：读取该 section 的清单与已知边界条件；每写一段代码对照清单确认覆盖；清单每条必须在代码中体现，或显式标注「不适用」并说明原因；先写边界条件处理（卫语句），再写主流程；代码结构镜像文档结构（section 级 → 类，子 section → 方法）；完成后设置 `code_ref`。
5. **逐条校验**：对清单每项在代码中搜索对应实现，记录 ✅ / ❌ / ⚠️；有 ❌ 或 ⚠️ 就补充修正后重验，最多 3 轮，仍无法通过则标记 `blocked` 并说明原因。
6. **执行记录**：清单 `- [ ]` 更新为 `- [x]`，追加校验记录，更新 manifest 状态。

## 工作流四：变更同步

- **代码先改**：通过 `code_ref` 定位 section → 反向翻译变更部分 → 更新清单与 `code_ref` → 检查受影响的关联 section。
- **文档先改**：修改 section → 正向翻译变更部分 → 更新代码与 `code_ref`。
- **定期对齐**：全量反向翻译后与文档逐 section 比对，输出差异清单（文档有而代码无、代码有而文档无、清单与实现不一致），再按清单更新文档或代码。

## 与其他 skill 的边界

`sunp-doc-project` 产出「给人看的项目全景」，用于接手与建立整体认识；本 skill 产出「给 AI 和开发者看的指定功能画像」，用于细节不丢失与双向翻译。两者都要时，先用 `sunp-doc-project` 建立全局，再用本 skill 深入具体功能。
