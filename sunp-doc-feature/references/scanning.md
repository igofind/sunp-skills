# 阶段一：扫描

范围确定后按本节逐项扫描，只读，不执行会改变仓库状态的命令。

## 扫描维度

| 维度 | 要找什么 |
|---|---|
| 定位与边界 | 功能做什么、不做什么、触发方式 |
| 流程与逻辑 | 主流程、关键分支、状态流转、业务规则 |
| 代码结构 | 入口、调用链、类与方法、文件位置 |
| 上下游 | 调用方、被调用方、外部接口 |
| 中间件 | 消息、缓存、搜索、调度、配置中心、注册中心 |
| 数据存储 | 表结构、缓存结构、读写路径 |
| 异常与边界 | 错误码、失败处理、并发、幂等、超时 |

中等功能走完一遍；大型功能或跨进程功能按链路抽样，并说明覆盖范围与未覆盖部分。

## 跨进程

下列任一情况成立时按跨进程处理：输入包含多个仓库；单个仓库内调用仓库外的服务；同一业务代码分布在多个服务中。

记录每处跨进程边界的发起方、承接方、协议与内容，以及数据最终归属哪个项目。每处结论标注所属项目，不按项目边界切割文档。

## 证据

结论要能回到代码或配置，按下列规则写证据。

**路径基准**：相对文档所在仓库根，不带 `../`，不从工作目录或父目录起算。跨仓库引用在路径前加项目目录名，例如 `renzi-data-handler/app-job/src/main/java/.../ApiUcController.java#addBusinessCircleMentorShip`。多个仓库并列在同一个父目录时，父目录不是仓库，不能作为路径基准。

**符号**：写到能唯一找到，默认写方法名或 XML 语句 id。同名方法按参数类型区分；一个文件含多个类时写成 `类.方法`；XML 语句与 DAO 方法同名时写明是哪一个。

**行号**：不写。行号随代码变动而失效，写错比不写更有害。需要定位到具体语句时，用方法名、条件描述或相邻符号说明位置。

**推断**：代码可见的事实与推断分开写。框架默认行为（必填参数、拦截器、全局异常处理）、框架让某个业务分支不可达、以及未在代码中闭环的调用，都标「推断」并写出依据。

**断言强度**：结论不能超过证据能支撑的范围。「订阅了某个主题」不等于「该主题会触发本功能」；「声明了接口」不等于「存在调用方」；「写了降级分支」不等于「线上会走到」。这三类结论必须标待确认，并写明缺哪一环证据。

不凭类名或注释断言功能已上线，也不把静态代码证据写成线上运行事实。
