# 阶段一：功能定位

阶段一只读：不修改文件，不执行会改变仓库状态的命令。遇到需要构建或安装依赖才能理解的项目，只读配置与锁文件推断，不执行安装、构建或测试。

定位解决两个问题：业务名称对应哪些代码符号，这批符号的边界到哪里。两个问题答不清，后面的扫描与写作都建立在猜测上。

## 检索路径

业务名和代码符号很少同名。「员工管理」落到代码里可能叫 `EmployeeController`，也可能叫 `StaffManageService`、`T_HR_EMPLOYEE`、`hr.employee.updated`。定位靠多条线索交叉，只做一次全文检索不够。

按线索面依次检索：

| 线索面 | 查什么 | 典型位置 |
|---|---|---|
| 声明面 | 路由与接口声明、RPC 服务声明、接口文档 | Controller 映射注解、Feign 或 Dubbo 接口、OpenAPI 定义 |
| 订阅面 | 消息主题、队列、定时任务、事件注册 | 监听器注解、任务注册类、事件总线订阅 |
| 配置面 | 菜单、权限点、网关路由、权限码常量 | 菜单配置、权限常量类、网关路由配置 |
| 数据面 | 表名、实体名、Mapper 或 Dao | MyBatis XML、实体类、建表脚本 |
| 调用面 | 上游系统对本接口的引用 | 跨仓库全文检索、客户端接口定义 |

每个线索面的做法：

1. 把功能名拆成可能的代码词，包括中文注释里的原词、英文词根与常见缩写，逐个检索。
2. 从任一命中符号出发向上找声明它的入口，向下找它调用的服务与存储。
3. 换一个线索面重做一次，确认两条独立线索指向同一批符号。

至少两条独立线索指向同一批符号才算定位成立。只有一条线索时按待确认处理，在调研发现里写明缺哪条线索、还检索过什么。

线索之间的冲突要当场澄清，不挑一个看起来合理的了事。同名的两个模块、复制出来的两套校验代码、只在一侧实现的旁路，都属于必须在阶段一说明的情况。

## 功能粒度

一个功能画像的定界单位是一个业务实体（通常是主表），加上它的主写操作，以及由主写操作派生的全部入口：页面、接口、消息订阅、定时任务、事件。

出现下列信号说明范围超出一个画像，需要拆分：

- 两个以上主实体，且各有独立生命周期
- 子流程之间不共享状态，可以单独上线或下线
- 入口分属不同业务域，由不同团队维护

超界时在阶段一给出拆分建议：建议拆成哪几个画像、各自覆盖哪些入口、依据是哪条信号。由用户选择，不自行拆分，也不把多个业务实体压进一篇。

## 失败分支

| 情形 | 动作 |
|---|---|
| 零匹配 | 列出候选（相近入口、相似命名、相关表），追问一次；仍无结果则中止，说明已检索的线索面与检索词 |
| 多处匹配 | 列出候选及各自特征，由用户选择；不自行合并成一个画像 |
| 输入是接口、表名或报错信息 | 以该符号为锚点反向扩散到功能边界，在调研发现里说明这是锚点式定位 |

中止时不给文档选项，不生成任何文档。候选清单要写清为什么这些符号可能相关，例如同名字段、同类表名前缀、注释里出现功能原词。

## 入口清单

阶段一把定位结果交给用户核对，用户才能判断范围是否正确。清单按入口类型分组，一类入口一行，不枚举同类接口的每个方法：

| 类型 | 入口 | 代码位置 | 所属项目 |
|---|---|---|---|
| HTTP | `POST /api/batch-transfer` | `wms-web/src/controller/BatchTransferController.java#transfer` | wms-web |
| 消息 | `wms.transfer.completed` | `wms-service/src/listener/TransferListener.java#onMessage` | wms-service |

代码位置按 `路径#符号` 写，路径相对该符号所在仓库根，跨仓库时加项目目录名前缀；不写行号。

清单之外但相关的入口单独列出，标明「本次不覆盖」及原因，例如只读查询接口、历史兼容入口、已下线的旁路。
