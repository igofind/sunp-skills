# 文档表达审查

## 用途与边界

审查一份已有文档的表达层质量：结论是否先行、术语是否准确、结构是否清晰、阅读是否顺畅，并给出可执行的改进建议。用于文档写完后的自查或润色，不负责从零生成文档。

只处理表达、语法、风格与阅读体验，不改文档的事实结论与技术内容。发现事实或逻辑问题时单独指出，交由用户确认，不擅自改写。

## 审查清单

逐项检查，只报确实存在的问题；不存在就跳过，不为凑数制造问题。

### 基本约定

- 使用中文，术语首次出现时给出必要解释。
- 结论先行：先给结论和下一步，再补依据；不让读者从大段内容中提取重点。
- 简洁：删除铺垫、套话、重复和与当前任务无关的内容。
- 基于事实：命令、路径、参数、接口、版本与执行结果要经代码、配置或运行结果核实；无法核实的标注为未验证，不把推测写成事实。
- 引用外部资料时给出来源，并把与结论相关的关键内容写出来，不只给链接。

### 读者与用途

- 开头写清文档给谁看、解决什么问题、读者拿它做什么。
- 正文只保留结论、关键依据、必要推导和最终做法；讨论过程、试错步骤和多轮修改不写入正文。
- 不假设读者在场：理解结论所需的上下文要补齐，但不复述无关背景。

### 组织与结构

- 按文档类型和读者任务决定章节；有通行结构时优先沿用，不自创结构。
- 每节先给结论，再说明依据；关键结论写清适用条件、限制和风险。
- 标题写内容，说明本节讲什么或得出什么结论；不用只有序号的标题，同级标题句式一致，层级不超过三级。
- 并列信息用列表，比较用表格，因果与推导用段落，操作流程用有序列表，代码和命令用代码块。

### 语法与措辞

- 句子完整、术语准确，避免口语化、含混指代和不必要的长句。
- 不使用「底层逻辑」「闭环」「抓手」「对齐一下」等不传递具体信息的表达。
- 同一概念全篇使用同一名称；缩写首次出现时给出全称。

### 阅读体验

- 篇幅以快速阅读为原则，只为理解确实重要的内容展开。
- 文档之间职责清晰，需要关联时用链接或引用，不重复解释同一件事。
- 交付前按读者视角自查：只读标题和每段首句，看能否还原文档结构和主要结论；再通读一遍，删掉与用途无关的段落和需要读者自行拼凑才能看懂的地方。

## 工作方式

1. 确认审查对象：文件路径或用户贴出的内容；没有就先问清楚。
2. 逐项过审查清单，记录问题位置与具体表现。
3. 按影响排序输出：先看是否影响读者理解结论，再看措辞和格式。
4. 用户要求直接润色时，在输出建议后按清单改进，并列出改动处。

## 输出

```
👉 结论
一句话给出总体判断：表达是否达标、主要问题在哪。

👉 问题清单
- <位置>：<问题> → 建议改法

👉 已改进（按需）
列出实际改动处；未直接润色时省略此节。
```

没有问题且用户未要求润色时，写「未发现表达层问题」并停止，不追加无关建议。
